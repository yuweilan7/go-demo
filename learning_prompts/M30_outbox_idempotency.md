## 必须讲解、实现和观察的内容

1. 先通过真实 MySQL/Kafka 复现两种双写坏顺序：DB 提交后发送失败、发送成功后 DB 回滚；网络返回失败不证明 broker 没接受。不能期待一个本地 Tx 或 Redis 锁包含整个系统。

2. 将订单变更+稳定 event_id 的 outbox 记录放同一 MySQL 事务，relay 从已提交记录发送 Kafka，收到适当确认后更新状态；发送后更新 outbox 前崩溃会重发，因此需要消费者幂等而非恰好一次幻想。

3. 消费者用 inbox/event_id 唯一约束+业务变更同事务，业务成功后提交对应 partition 的安全 offset；处理中崩溃、业务已成功但 offset 未提交都必须可重投。inbox 插入成功但效果失败必须整体 rollback。

4. 若多个 relay 并行，给领取/lease/CAS 或受控 SKIP LOCKED 的明确协议，处理过期 owner 与重复投递；同一聚合版本的事件乱序需检测并按业务契约处理。未核验高级领取前先用单 relay，不能为吞吐引入虚假保证。

5. 真实验收重复下单、duplicate event、DB commit/producer confirm 后不同崩溃窗口、消费者重启及最终查账；断言订单数、扣减量、inbox/outbox/offset，不仅看日志。练习：补一个崩溃时间线；修复先 offset 后 commit；设计未知请求的查询接口。Saga 补偿只给实际不可回滚场景的状态图，不造通用框架。
