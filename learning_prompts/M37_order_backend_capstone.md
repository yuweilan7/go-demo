## 必须讲解、实现和观察的内容

1. 限定一个小电商业务：创建订单/查询状态/库存扣减/订单事件/缓存查询。采用 Gin API+真实 MySQL/GORM+Redis+Kafka+一个真实只读库存 gRPC；权威库存扣减和订单/outbox 在订单用例的同一 MySQL Tx 内完成，RPC 查询结果不能充当锁定库存或跨服务事务。不模拟支付、不做商城 UI、不造微服务平台。框架迁移留 M32 或后续实际需要。

2. 先给一张数据流和资源 ownership 图，再分步组装：HTTP 输入/归属 → usecase → 同事务订单/库存/outbox → relay → Kafka → 幂等 consumer → 查询缓存。确定哪个数据库字段是权威事实、哪些值可重建。

3. 复用前置的已验契约与机制，建立本模块唯一的业务实现；不把完整实验复制成多个服务，也不并行修改其他 lesson。为并行前置通过本地 replace 引入必要库或提炼到本课明确职责，不建立循环依赖。

4. 写出 request_id/event_id/order_id/aggregate_version 的关系、订单有限状态、金额/币种、整体预算和错误映射；HTTP/RPC 中 request ctx、后台 relay 服务 ctx、SQL Tx、共享客户端都有明确 owner。

5. 正常验收下单/查询/库存守恒、幂等请求、重复事件、用户隔离、缓存失效和关闭。验收客户端内容、DB 行、消息 offset/处理记录与资源退出，不能只跑 happy path HTTP 200。练习：追一条真实订单；安全新增字段；说清哪个失败窗口留下 UNKNOWN。故障矩阵由 M38 深入，先把最小链路跑扎实。
