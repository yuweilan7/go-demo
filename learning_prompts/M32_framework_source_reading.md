# M32：真实微服务框架：Kratos 主线，Kitex/go-zero 迁移阅读

我是熟练的 Java 后端工程师，刚开始系统学习 Go，准备在 Shopee 阅读和维护复杂后端业务。我理解 Java 的线程池、异常、Spring、事务及常用中间件，但不能假定我懂 Go 的对应机制；已有示例出现过某语法也不等于我掌握了它。请以 Go 自身语义为主，用 Java 类比加速理解，并说清类比失效的地方。目标是让我能读真实代码、预测运行行为、定位错误和做有证据的小改动。

只完成本模块。先读适用的 AGENTS.md、根 README/go.mod、本模块已有交付及下方指定材料；files/ 是启发材料，必须纠正错误、版本差异和未经证实的绝对化结论。教学默认 Go 1.27；重新核对 go version、go env、模块 go/toolchain 指令和官方文档，区分语言保证、库契约及运行时实现。遇到公司旧版本代码，按其实际版本解释，不擅自升级。第三方依赖锁定实际可运行版本，不能凭记忆混用 API。

本模块交付中文 README.md、带详细中文注释的 Go 源码、可运行实验和必要的独立断言，STATUS.md 记录实际运行结果。复杂机制按“业务场景 → 最小规则 → 预期时间线 → 错误复现 → 修复对照 → 实际业务影响”递进，原理、反例、修复及完整解析直接放在文档和实验中。每课保留一个可在 10～20 分钟运行并讲清的核心实验，扩展分步展开。

所有手写 Go 教学代码都要采用 Python 学习项目那种详细、通俗的中文注释，包括实验入口、业务函数、并发协调、资源清理和关键断言。每个非平凡函数先说明在业务/实验中的职责、谁调用、参数从哪来、结果给谁以及拥有何种资源；在关键语句旁讲透变量是值副本还是共享对象、当前状态、为何选择该分支、在哪一行等待、错误/取消/panic 如何传播、defer 何时执行以及谁负责收尾。Go 小白不熟悉而本课正在使用的语法和 API 也要就地解释，如 := 的作用域、接收者、接口动态值、闭包捕获、channel 方向、返回值或驱动结果；不能只写“处理错误”“关闭连接”“启动协程”。简单且已讲清的赋值不重复凑字数，第三方和生成代码只解释相关入口与契约，不批量改注释。

README 从入口到真实副作用给出阅读顺序和带符号定位的完整调用链；并发/事务/消息实验按时间顺序列出“哪个参与者 → 当前函数/等待点 → 状态或资源变化 → 下一步为何发生”。对照实际日志、SQL/键值/消息和断言逐段解析正常、错误、取消与清理路径，说明不保证的调度顺序及 Java 类比的失效处。以上标准在本 prompt 内即可执行；仓库内的 [中文教学与源码注释规范](TEACHING_STYLE.md) 提供更具体的要求和注释示例，执行时一并读取。

在下方目标目录创建独立 Go module，module 路径为 go-demo/lessons/目录名，默认入口 cmd/demo，按必要职责拆包。仅修改本模块目录；不改根 go.mod/go.sum、全局索引、其他模块和原 examples/files。依赖前置的源码时采用本模块内明确的本地 replace 或文档约定，禁止建立循环导入、复制整套前置项目或修改共享 go.work。并行运行时各自使用独立端口、数据命名空间、配置和报告；根 go test ./... 不包含这些嵌套 module。使用独立 worktree 或明确的目录隔离，不切换其他任务的分支、不提交或清理他人文件。

用 gofmt，实际执行 go -C 目标目录 run ./cmd/demo 和相关 go test/go vet；并发课在平台支持时执行 -race，遇到工具链限制报告精确原因。坏例子放显式故障入口或子进程，正常入口保持可用；所有阻塞实验有上限，并用屏障/可观察状态控制顺序，不能用 sleep 猜调度。中间件课必须使用真实服务和真实驱动；本地 HTTP/RPC 进程是实际协议实验，纯函数替身只可辅助单测，不能冒充实库、真实 MQ 或故障验收。按实际结果写 STATUS.md，记录版本、命令、结果、未验范围和资源清理，不以编译通过、HTTP 200 或健康检查代替业务正确性。

## 必须讲解、实现和观察的内容

1. 如果用户或目标仓库已指定框架则优先沿用；否则默认 Kratos，以显式构造、HTTP/gRPC transport 和 lifecycle 衔接前置。不要宣称 Shopee 一定使用它，框架选型只是教学默认。

2. 运行真实框架最小服务，保持前置库存 RPC/业务接口的语义和失败断言；按实际版本锁定 generator/runtime/插件，解读目录、generated 注册、config/provider、biz/data、启动和 cleanup。框架生成器只向本模块目录写。

3. 选一条真实请求，定位 client → transport → middleware → service/usecase → repository → error 返回的文件和符号，标明 interface/function options/context/error/资源释放发生位置；不能用自写伪框架代替源码。

4. 实测一个业务 error、panic、request timeout 和服务停止，区分框架默认处理与业务应补的职责。自动重试、缓存、事务、注册/发现不能仅凭配置存在就标已生效。

5. 对 Kitex 和 go-zero 各读一个官方最小调用签名与 lifecycle/治理路径，与主线作短表比较；只深跑一个框架，若公司指定 Kitex/Thrift 等则替换主线并核验实际生成器。文档沿实际错误传播和 cleanup owner 示范从框架入口定位 ctx、重试和 SQL；框架排行榜与全源码遍历不作为验收。
